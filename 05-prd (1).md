# Product Requirements Document (PRD)

**Project:** OTT Comparison & Discovery Platform
**Phase:** Epic 3 — Product Requirements Document
**Builds on:** `03-product-discovery-report.md`, `04-product-strategy-mvp.md`
**Status:** Draft v1.0

---

## 1. Executive Summary

Users currently spend excessive time deciding what to watch because the information they need is split across three disconnected sources: genre-based discovery, trusted rating sites (IMDb, Rotten Tomatoes), and individual OTT platform searches to confirm availability. This PRD defines the requirements for an MVP web application that solves this by presenting a single, genre-filtered comparison table showing ratings, platform availability (Netflix, Amazon Prime, Disney+ Hotstar), format (movie/series), and content origin — for every title, in one view.

The MVP is intentionally narrow: three platforms, two rating sources, no user accounts, no personalization. This scope is designed to validate one core hypothesis — that collapsing multi-source research into a single table meaningfully reduces the time it takes a user to go from "I want to watch something" to "I've picked something." Success will be measured primarily through median search-to-selection time (see Section 5).

This document translates the product vision and MVP scope (Epic 2) into concrete functional and non-functional requirements to guide design (Epic 4) and development (Epics 5–6).

## 2. Product Scope

### 2.1 In Scope (MVP)
- Genre-based search and filtering
- Movies and Series as separate, explicitly segmented sections
- Comparison table per title showing: title, genre, format, origin/language, IMDb rating, Rotten Tomatoes rating, availability flags for Netflix / Amazon Prime / Disney+ Hotstar
- Default sorting by rating, high to low
- Basic secondary sort/filter controls (e.g., by platform, by origin)
- Responsive web interface (desktop + mobile browser, not a native app)

### 2.2 Out of Scope (MVP)
- User accounts, login, or authentication
- Personalized recommendations or watch history
- Watchlists, saved searches, or social/sharing features
- Additional OTT platforms beyond the initial three
- Additional rating sources beyond IMDb and Rotten Tomatoes
- Native mobile applications
- Multi-language UI (interface itself is English-only for MVP; content origin/language is metadata, not a UI localization feature)

### 2.3 Scope Boundary Rationale
Every in-scope item maps directly to collapsing the three-step research process identified in discovery (genre → rating → availability). Anything not directly serving that collapsed workflow is deferred, per the MVP definition in Epic 2, to avoid scope creep before the core hypothesis is validated.

## 3. Functional Requirements

| ID | Requirement | Description | Priority |
|---|---|---|---|
| FR-01 | Genre-based search | User can select or search by genre (e.g., Thriller, Comedy, Drama) to filter results | P0 |
| FR-02 | Format segmentation | Results are clearly split into "Movies" and "Series" sections/tabs | P0 |
| FR-03 | Comparison table display | Each result row displays: title, genre, format, origin/language, IMDb rating, Rotten Tomatoes rating, and availability status (Yes/No or platform icon) for Netflix, Amazon Prime, and Disney+ Hotstar | P0 |
| FR-04 | Default sort by rating | Table results are sorted by rating, high to low, by default on load | P0 |
| FR-05 | Manual sort controls | User can re-sort the table by any column (e.g., by platform availability, by origin) | P1 |
| FR-06 | Platform filter (dropdown/selection) | User can filter results to only show titles available on a specific platform they select from a list/dropdown | P1 |
| FR-07 | Origin/language display | Each title's country of origin/language is visible in the table without requiring a click-through | P1 |
| FR-08 | No-results handling | If a genre search returns no results, the system shows a clear empty state rather than a blank table | P1 |
| FR-09 | Title detail view (now MVP-level, combined with FR-13) | Clicking a title shows expanded info (synopsis, cast, full rating breakdown) and serves as the surface for the trailer preview (FR-13) | P1 |
| FR-10 | Data freshness indicator | Table or footer indicates when availability/rating data was last updated, so users can gauge reliability | P2 |
| FR-13 | Inline trailer preview | Clicking a title opens an option to watch its trailer directly within the same view (e.g., embedded player or modal), without navigating away from the comparison table | P1 |
| FR-11 | Timeline/release-year filter | User can filter results by release year or year range (e.g., "after 2000," or a custom range) in combination with genre | P1 |
| FR-12 | One-click platform icon filter | User can click directly on an OTT platform's icon/logo (Netflix, Prime, Hotstar) to instantly filter the table to only that platform's available titles, without opening a separate dropdown | P1 |

*Note: FR-06 and FR-12 both filter by platform but serve different interaction patterns — FR-06 is a deliberate dropdown selection (useful when combined with other filters), while FR-12 is a fast, one-tap shortcut for users who already know which platform they want (directly serves the "Time-Starved Professional" persona). Design (Epic 4) should decide whether both are needed in the MVP or whether FR-12 supersedes FR-06 for simplicity — flagged as an open question in Section 6.*

### 3.1 Acceptance Criteria (Sample — Core Requirements)

**FR-01 — Genre-based search**
- Given a user lands on the homepage
- When they select or type a genre
- Then the system returns only titles matching that genre, split by Movies/Series

**FR-03 — Comparison table display**
- Given genre results are returned
- When the table renders
- Then every row shows rating (IMDb + Rotten Tomatoes), platform availability for all three platforms, and origin — with no missing columns for any listed title

**FR-04 — Default sort by rating**
- Given the table has loaded
- When no manual sort has been applied
- Then titles appear ordered from highest combined/primary rating to lowest

**FR-11 — Timeline/release-year filter**
- Given a user has selected a genre
- When they set a release-year filter (e.g., "after 2000" or a specific range)
- Then the table only shows titles matching both the genre and the year criteria
- And the rating-based default sort still applies within those filtered results

**FR-12 — One-click platform icon filter**
- Given the comparison table is displayed with platform icons visible (Netflix, Prime, Hotstar)
- When a user clicks/taps a specific platform's icon
- Then the table instantly filters to show only titles available on that platform
- And existing genre/year filters remain applied (filters combine, they don't reset each other)
- And clicking the same icon again (or a "clear filter" control) removes the platform filter

**FR-13 — Inline trailer preview**
- Given a user clicks on a title in the comparison table
- When the title's detail view/modal opens
- Then a "Watch Trailer" option is immediately visible
- And selecting it plays the trailer within the same view (embedded player or modal), without redirecting to an external site or app
- And the user can close the trailer and return to the comparison table without losing their applied filters (genre, year, platform)

*Note: FR-13 is closely tied to FR-09 (title detail view) — in practice, the trailer option will likely live inside that same detail view/modal rather than as a fully separate interaction. Design (Epic 4) should treat these as one combined "title detail" surface rather than two separate UI patterns.*

## 4. Non-Functional Requirements

| ID | Category | Requirement |
|---|---|---|
| NFR-01 | Performance | Comparison table must load within 2–3 seconds under typical conditions, since page load time is a guardrail metric tied directly to the product's core value proposition (speed) |
| NFR-02 | Data Accuracy | Availability and rating data must be refreshed on a defined schedule (e.g., daily or per data-source update cycle) to avoid showing stale/incorrect platform availability |
| NFR-03 | Responsiveness | UI must render usably on both desktop and mobile browser widths, without requiring a native app |
| NFR-04 | Scalability | Data layer should be structured to allow additional platforms/rating sources to be added post-MVP without a full architecture rebuild |
| NFR-05 | Availability/Uptime | Application should target reasonable uptime for a portfolio-stage MVP (formal SLA not required, but no prolonged unplanned downtime during demo/review periods) |
| NFR-06 | Privacy/Compliance | If any analytics or usage tracking is added (per Epic 8), data collection must comply with applicable privacy expectations — no collection of personally identifiable information without disclosure |
| NFR-07 | Maintainability | Codebase and data schema should be documented well enough for a small team (or solo developer) to extend post-MVP, given the project's team-size constraint noted in Epic 2 |
| NFR-08 | Accessibility (baseline) | Table should use readable contrast and semantic markup at a basic level, even if full WCAG compliance is not an MVP requirement |

## 5. Success Metrics

*(Carried forward from Epic 2 strategy, restated here for PRD completeness — see `04-product-strategy-mvp.md` for full detail)*

- **North Star Metric:** Median time from genre search to title selection
- **Leading metrics:** Genre searches per session, sort/filter interaction rate, table page bounce rate
- **Lagging metrics:** Return usage rate, session-to-selection completion rate
- **Guardrail metrics:** Data accuracy rate, page load time (directly maps to NFR-01 and NFR-02 above)

Each functional requirement above should be traceable back to at least one of these metrics — for example, FR-04 (default sort) directly supports the North Star Metric by reducing the manual sorting/scanning step users currently perform themselves. Similarly, FR-11 (timeline filter) and FR-12 (one-click platform icon filter) both reduce clicks-to-decision, which is the same underlying signal the North Star Metric captures — worth tracking as a leading metric how often each filter is used, since low usage of either could mean it's not solving a real need.

## 6. Open Questions for Design & Engineering (Epic 4/5)

- What data source(s) will supply platform availability reliably (API vs. licensed data vs. manual curation)? This was flagged as a top risk in Epic 2 and should be resolved before high-fidelity design begins.
- Should "availability" be binary (yes/no) or include additional info (e.g., rental vs. subscription-included) — out of scope for MVP but worth flagging for V2.
- Confirm whether IMDb/Rotten Tomatoes data can be sourced within budget/legal constraints for a portfolio project (rate limits, licensing, scraping restrictions).
- Decide in Epic 4 whether FR-06 (dropdown platform filter) and FR-12 (one-click icon filter) both ship in MVP, or whether the icon-click shortcut alone is sufficient to keep the UI simpler.
- Identify a reliable trailer source for FR-13 (e.g., YouTube embed via a movie-database API like TMDB) and confirm embedding is technically and legally straightforward before committing this to MVP scope in Epic 5.
